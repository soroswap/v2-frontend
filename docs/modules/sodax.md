# SODAX Swaps Module

> **Living document.** Read this before modifying the module. Update it in the same change whenever the module's behavior, endpoints, files, or dependencies change.

**Source:** `src/features/sodax/`, `src/app/api/sodax/` · **Last verified:** 2026-09-10

## Purpose

Routes swaps for a curated set of Stellar assets — SODA plus 24 tokenized stocks, ETFs, and crypto majors — through the SODAX solver instead of the Soroswap AMM, inside the same swap card the rest of the app uses. `lib/pair.ts`'s `isSodaxPair` decides, per selected pair, whether a swap goes through SODAX (`useSodaxSwapIntegration`) or the existing Soroswap flow (`useQuote`/`useSwap`); `src/features/swap/hooks/useSwapController.tsx` holds both and switches between them (`hooks/useSwapController.tsx:128-135,292-310`). A pair routes through SODAX when both sides are SODAX registry assets, or one side is a registry asset and the other is XLM or USDC (`lib/pair.ts:20-33`).

## Key methods

- **The asset registry** (`constants/assets.ts:45-221`) is a hand-maintained `SEEDS` array of 25 assets — SODA, 8 tokenized stocks (`category: "stock"`), 5 ETFs (`"etf"`), 11 crypto majors (`"crypto"`) — generated from the live SODAX token list cross-checked against each contract's SAC `name()` (`:1-16`). Every entry shares `SODAX_STELLAR_ISSUER` and 7 decimals (`:37-41,229-234`). Re-verify the whole table against production with `node scripts/sodax-assets-check.mjs` (Testing) before editing it by hand.
- **`isSodaxPair(contractA, contractB)`** (`lib/pair.ts:20-33`) is false if either side is missing, equal, or neither side is a registry asset; true if both sides are registry assets; otherwise true only if the non-registry side is XLM or USDC (`SODAX_COUNTERPART_CONTRACTS`, `constants/sodax.ts:73-76`). It is keyed off the **static** registry table regardless of the live token list `useSodaxAvailability` fetches (`lib/pair.ts:7-19`) — see that bullet below.
- **`useSodaxAvailability(options?)`** (`hooks/useSodaxAvailability.ts:29`) is the feature's graceful-degradation gate: the SWR key is `null` (query disabled) unless `isProductionEnv && enabled` (`:32`; `enabled` defaults to `true`, and `TokenSelectorModal` passes `{ enabled: includeSodaxTokens }` so a picker that never offers SODAX assets — e.g. pools add-liquidity — never fires `GET /api/sodax/tokens`, `src/features/swap/TokenSelectorModal.tsx:34-38`), and `isSodaxEnabled` additionally requires no error and a non-empty live token list (`:43`). `availableAssets` (`:53-59`) is the registry filtered to contracts the live list actually has — **this filters what the token selector offers only.** Routing (`isSodaxPair`) does not consult this list: a registry contract the user already selected (typed directly, or picked before it was delisted) still routes through SODAX by design, and can fail to quote rather than falling back to the AMM (`:45-52`).
- **`useSodaxSwapIntegration(...)`** (`hooks/useSodaxSwapIntegration.tsx:73`) forces sell-side driving: `inputAmount` is only computed when `independentField === "sell"` (`:107-110`), because SODAX quotes `exact_input` only. `destinationTrustlineAsset(buyContract)` (`:58-66`) returns `null` for XLM, the registry asset for a registry contract, `USDC_STELLAR` for USDC — the trustline gate only ever checks the **destination** (buy) side, since selling implies the source trustline already exists (`:175-177`). `quoteErrorMessage` (`:146-162`) renders `"No route for this direction yet"` when the sell side is a registry asset other than SODA (`isNonSodaSellGap`, `:135-141`) and the generic dust-amount wording otherwise. It also snapshots what was actually submitted into `sodaxRunSummary` at the start of `handleSodaxSwap` — `{ sellToken, buyToken, sellAmount, buyAmount }` (`:217-222`) — so the completion screen (`SodaxSwapModal`, wired up in `src/app/page.tsx:319-334`) can't drift onto live form state the user changed after Dismiss; `resetSodaxSwap` (`:258-261`) clears both the execution machine and this snapshot together.
- **`useSodaxSwap().executeSodaxSwap(params)`** (`hooks/useSodaxSwap.tsx:390`) is the execution state machine — see below.
- **`useSodaxUsdPrice(contract)`** (`hooks/useSodaxUsdPrice.ts:15`) fetches the USD price from the cached server route (`GET /api/sodax/price`, via `fetchSodaxUsdPrice`, `lib/api.ts:156-161`) rather than quoting the solver client-side — the server does the 100 USDC → asset probe and caches it for 120 s (`:8-13`). Inert (`price: null`, not loading) for any contract that isn't a registry asset (`:33-39`).
- **`useSodaxTrustline(asset)`** (`hooks/useSodaxTrustline.tsx:59`) tags every `checkTrustline()` call with a `requestIdRef` (`:84,87,101,133`) so a slow response for a stale (asset, account) pair can't overwrite fresher state; the triggering effect resets `trustlineStatus`/`hasCheckedOnce`/`checkError` synchronously on every asset/account change, before the fresh check starts (`:210-223`). A missing account is recognised by the SDK error's identity — `isHorizonNotFound` checks `error.name === "NotFoundError"` or `response.status === 404`, never the message text, which the SDK sets to "Not Found" (`:64-70,160`) — and takes the confirmed-empty path. Any other Horizon failure (rate-limit, network blip) sets `checkError` and leaves `hasCheckedOnce` false, so the flow reads "unknown, retry" rather than a false "no trustline, 0 XLM" (`:158-171`); `SodaxTrustlineSection` renders that state with a "Retry check" button wired to `checkTrustline` (`components/SodaxTrustlineSection.tsx:37-55`). Reserve maths derives `spendableXlm = balance - (2 + subentry_count + num_sponsoring - num_sponsored) × 0.5` from the Horizon account (Stellar's minimum-balance formula, sponsorship included); `hasInsufficientReserve` fires when that's below `TRUSTLINE_RESERVE_XLM` (0.5) + `FEE_HEADROOM_XLM` (0.1) (`:131-142,245-247`).

**Execution state machine.** `useSodaxSwap.executeSodaxSwap` (`hooks/useSodaxSwap.tsx:390-580`) drives `SodaxSwapStep` (`:29-40`) through, in order:

1. `PREPARING` — fetch a provisional deadline, `checkSodaxAllowance` (`:416-423`).
2. `APPROVING` (only if the allowance check failed) — `fetchSodaxApproveTx`, sign, broadcast via `sendTransaction`/`/api/sodax/send`, then re-check allowance rather than assume it landed (`:427-443`).
3. `CREATING_INTENT` — fetch a _fresh_ deadline and `createSodaxIntent`, timed to start as close to the signature as possible so the deadline window isn't burned by steps 1-2 (`:451-462`).
4. `WAITING_SIGNATURE` — the user signs the intent tx (`:465-475`).
5. `SENDING_TRANSACTION` — broadcast the signed intent tx via `/api/sodax/send` (`:477-514`). This step has a **post-broadcast concept** the earlier steps don't need — see below.
6. `SUBMITTING_TO_SOLVER` — `submitSodaxTx` hands the broadcast tx to the relay, retried up to 3× with linear backoff on transport/5xx failures (`SUBMIT_ATTEMPTS`, `SUBMIT_RETRY_BASE_MS`, `:210-211,516-548`).
7. `WAITING_FOR_FILL` — poll `/api/sodax/submit/status` every `SODAX_STATUS_POLL_INTERVAL_MS` (3 s) until `"solved"`, `"failed"`, `intentCancelled`, `abandonedAt`, or `SODAX_STATUS_POLL_TIMEOUT_MS` (5 min) elapses (`:315-388,550-562`). Any failure here is forced non-retryable and carries `srcTxHash` (`:555-561`), since the intent is already on-chain by this point.
8. `SUCCESS` / `ERROR` — terminal (`:564-578`).

**Post-broadcast semantics (step 5 onward).** Once the intent transaction may have reached the network, a retry means signing a _second_ intent against funds already committed to the first — so from `SENDING_TRANSACTION` on, the machine stops defaulting to "retryable":

- `hashOfSignedXdr` (`:200-208`) computes the Stellar transaction hash locally, before the broadcast call, so the client knows which transaction to track even if the call itself fails.
- `sendTransaction` (`:303-318`) posts to `/api/sodax/send` with a **55 s** ceiling (`SODAX_BROADCAST_TIMEOUT_MS`, `constants/sodax.ts:27-35`) instead of `lib/api.ts`'s 20 s default — it must exceed the route's worst case (below), or the client would abort a broadcast the network may still land.
- Only two outcomes prove the network did **not** take the transaction, and stay retryable: the route's explicit 400/503 `SODAX_ERROR_SUBMIT` (`isDefinitiveRejection`, `:176-182`), and a `BroadcastRejected` — the tx landed in a ledger and failed there, so only the fee was spent (`:160-167,309-311`). Every other failure — timeout, dropped connection, a 5xx, the route's own `SODAX_ERROR_BROADCAST_UNKNOWN` — is treated as "may be on-chain": if a local hash was computed, execution carries on to the relay handoff with that hash and `broadcastConfirmed = false` (`:490-514`); if even the local hash is unavailable (unparseable XDR — a case the wallet would already have refused to sign), it fails non-retryable with `BROADCAST_STATE_UNKNOWN_MESSAGE` (`:213-214,501-508`).
- The relay handoff (step 6) retries transient failures (`isTransientSubmitFailure`: `NETWORK_ERROR`, `TIMEOUT_ERROR`, or any 5xx, `:185-192`) up to 3× with linear backoff (`SUBMIT_RETRY_BASE_MS * attempt`); a non-transient failure, or exhausting the retries, fails non-retryable with `HANDOFF_FAILED_MESSAGE` and `srcTxHash` (`:215-216,541-546`).
- `failWith`'s `override` parameter (`:258-290`) lets a post-broadcast failure force `retryable: false` and attach `srcTxHash`, regardless of what the underlying transport error would otherwise classify as.
- `SodaxSwapError.retryable` (`:65-82`) is `false` for every such failure. `SodaxSwapModal` reads it to label the terminal button **"Close"** instead of **"Try Again"** whenever `step === SUCCESS` _or_ `error?.retryable === false` (`components/SodaxSwapModal.tsx:258-260`), and renders a `TxLinks` explorer link + copy-hash affordance (`:56-75`) whenever `result.srcTxHash` (SUCCESS, `:201`) or `error.srcTxHash` (ERROR, `:208-211`) is set, so the user can check the transaction before doing anything else.

`/api/sodax/send`'s own budget (server-owned, `src/app/api/sodax/send/route.ts`): `maxDuration = 60` (`:7`), a 30 s `CONFIRM_TIMEOUT_MS` poll on the normal accept path (`:10-11`), a 15 s per-RPC-call `RPC_TIMEOUT_MS` enforced by `withTimeout` because `rpc.Server` ignores its own `timeout` option at runtime (`:22-46,68-72,168`), and a 6 s `UNKNOWN_STATE_PROBE_MS` when `sendTransaction` itself throws — the route computes the hash before submitting (`:162`) and probes the ledger for it (`:59-84`) before answering, so a proxy error or socket reset doesn't have to mean "not sent". Worst case is therefore ~15 s submit + 30 s confirm + one poll interval, which is why the client ceiling is 55 s. Its documented error contract is exactly what the client's `isDefinitiveRejection` (`hooks/useSodaxSwap.tsx:178-189`) relies on: the route's own pre-submit refusals (`SODAX_ERROR_PARAM`, `SODAX_ERROR_CORS`) and 400/503 `SODAX_ERROR_SUBMIT` mean the network definitively did not take the transaction; 502 `SODAX_ERROR_BROADCAST_UNKNOWN` (with `context.txHash`) means it may have. While polling for the fill, a 404 from the status route (the relay has no record of the hash yet) is not counted as a connection failure (`:341-346`); only the poll timeout's `broadcastConfirmed`-aware message speaks to a transaction that never landed.

Steps 2 and 5 both broadcast a signed Stellar transaction, and they deliberately use different endpoints than the rest of the app (`src/app/api/sodax/send/route.ts:60-69`):

- **`/api/sodax/send`** submits straight to Soroban RPC (`rpc.Server(STELLAR.RPC_URL).sendTransaction`, `:135,140`) because the generic `/api/send` proxies Soroswap's send API, which rejects Soroban transactions that don't touch a Soroswap contract — every SODAX intent invocation does. It allowlists exactly `invokeHostFunction`, `extendFootprintTtl`, `restoreFootprint`, `changeTrust` (`:26-31`) — the intent invocation, its TTL footprint helpers, and the source-side trustline approval leg — and 400s on anything else, so it can't become a general-purpose broadcast relay.
- **`/api/send`** (Soroswap's route) is used only by `useSodaxTrustline.createTrustline` (`hooks/useSodaxTrustline.tsx:182`) for the **destination** trustline the user adds manually — a plain classic `changeTrust` unrelated to the SODAX intents contract — and by the rest of the app's ordinary Soroswap flow.

**No-route (422) behavior.** The solver returns HTTP 422 `"No path was found"` for two distinct cases that `useSodaxSwapIntegration` cannot fully distinguish from the status code alone:

- **Dust-sized amounts.** `scripts/sodax-quote-check.mjs`'s smallest passing cases are 10 USDC (`:50,59`) — so treat anything much below roughly 10 USDC-equivalent as liable to 422 regardless of pair. The server-side USD-price probe reflects the same ceiling: it quotes 100 USDC, not 1, because a dust-sized probe can itself 422 on some pairs (`hooks/useSodaxUsdPrice.ts:8-13`).
- **The sell-direction gap.** Selling any registry asset other than SODA (any of the 24 newly listed stocks/ETFs/crypto as the _source_ token) currently 422s at every size — a SODAX-side solver gap under investigation, not a bug in this app (`scripts/sodax-quote-check.mjs:103-107`). `isNonSodaSellGap` (`hooks/useSodaxSwapIntegration.tsx:135-141`) detects it; `quoteErrorMessage` renders `"No route for this direction yet"` for that case and the generic `"No route found — try a larger amount"` for every other 422 (`:143-162`); `sodaxQuoteErrorHint` adds explanatory copy for the same gap — `` `The SODAX solver couldn't find a route to sell ${code} right now — this direction may not be available yet.` `` (`:164-173`) — shown in `src/app/page.tsx:240-244`.

## Gotchas & invariants

- **Graceful degradation is the whole feature's safety net.** `useSodaxAvailability`'s SWR key is `null` on testnet (`hooks/useSodaxAvailability.ts:32`), so on testnet — and on any `SODAX_SWAPS_API_URL` misconfiguration, or while the live token list is empty or erroring — `isSodaxEnabled` is `false`, no SODAX asset enters the token selector, and `isSodaxPair` can never see a registry contract in user input. Do not bypass this gate to "test SODAX on testnet"; the asset registry is mainnet identities only.
- **SODAX quotes `exact_input` only** (`types/sodax.ts:57`, hardcoded in `useSodaxQuote`, `hooks/useSodaxQuote.ts:50`). `useSodaxSwapIntegration` enforces this by only computing `inputAmount` when the Sell field is independent (`hooks/useSodaxSwapIntegration.tsx:107-110`); `useSwapController` backs this up by snapping `independentField` back to `"sell"` whenever a SODAX pair becomes active while the Buy field was driving, carrying the typed value across rather than clearing it (`src/features/swap/hooks/useSwapController.tsx:137-146`). `SwapPanel`'s Buy side is also rendered with `inputDisabled` when `sodax.isSodaxActive` (`src/app/page.tsx:222`) and shows a one-line "Amount is set by the Sell side for SODAX swaps" note while disabled (`src/features/swap/SwapPanel.tsx:155-159`), so the user can't type there either and is told why.
- **Selling anything but SODA currently has no route** (the sell-direction 422 gap above). This is a live product gap, not a display bug — do not "fix" it by hiding the sell option for those assets; the copy in `useSodaxSwapIntegration.tsx:135-173` is the intended UX until the solver accepts these assets as a source.
- **A retry is never offered once funds may be committed.** See "Execution state machine" above — `SodaxSwapError.retryable` (and its `override` in `failWith`, `hooks/useSodaxSwap.tsx:258-290`) governs the modal's Close/Try Again label and whether the ERROR screen implicitly invites a second signature. Do not add a blanket retry action to the terminal ERROR state without checking `retryable` first.
- **A non-404 trustline-check failure must never be read as "no trustline, zero balance."** `useSodaxTrustline` distinguishes the two explicitly (`hooks/useSodaxTrustline.tsx:64-70,158-171`) via `checkError`, and detects the 404 by the SDK error's name/response status, never by message text; collapsing them back together reintroduces a dead-end "Not enough XLM ... 0.00 XLM" state with no recovery path — the exact bug this fixed.
- **The origin guard is anchored to the parsed host, not a substring match.** `sodaxOriginGuard` (`src/shared/lib/server/sodaxClient.ts:67-79`) parses `Origin`/`Referer` with `new URL()` and compares the resulting `host` against `ALLOWED_ORIGINS` — exact match, or dot-suffix match for `.soroswap.finance`-style entries (`:40-61`). This is deliberately stricter than the substring check (`origin.includes(allowed)`) the older Soroswap/earn routes use inline (see api.md): the comment explains why — `/api/sodax/send` broadcasts straight to Soroban RPC, where a substring check would let `https://evil.com/?x=app.soroswap.finance` through (`:33-39`).
- **`/api/sodax/send` rejects a well-formed transaction that isn't SODAX's.** Its `ALLOWED_OPERATIONS` allowlist (`src/app/api/sodax/send/route.ts:26-31`) is intentionally narrow so this endpoint can't become a general broadcast relay; adding a new SODAX flow with a different operation type needs this list extended deliberately, not worked around.
- **`SodaxSwapModal`'s dismiss state is derived during render, not in an effect** (`components/SodaxSwapModal.tsx:142-152`), so it applies before the first paint of a new step and avoids `react-hooks/set-state-in-effect`. Dismissing only hides the modal locally; it never cancels an in-flight swap, which keeps running in the background (`:131-141,264-278`).
- **`useSodaxTrustline`'s reserve check derives from the account's real Stellar reserve**, not a flat guess: `spendableXlm = balance - (2 + subentry_count + num_sponsoring - num_sponsored) × 0.5`, compared against `TRUSTLINE_RESERVE_XLM` (0.5) + `FEE_HEADROOM_XLM` (0.1) (`hooks/useSodaxTrustline.tsx:20-23,131-142,245-247`). If Stellar's base/subentry reserve amounts ever change via protocol amendment, these constants need revisiting alongside it.
- **`getSodaxClient()` is a module-scope singleton, constructed once on first use.** If `SODAX_API_KEY` is added to a running server's environment after the client has already been built, that process keeps using the headers it started with (`src/shared/lib/server/sodaxClient.ts:13-31`).

## Testing

No automated tests exist in this repo. Two read-only scripts verify the integration against the live SODAX API without a wallet:

- **`node scripts/sodax-assets-check.mjs`** (needs `SODAX_SWAPS_API_URL`, e.g. via `--env-file=.env.local`) re-verifies every registry entry in `constants/assets.ts` against `GET /swaps/tokens/stellar` (symbol, decimals) and each contract's on-chain SAC `name()` (must equal `CODE:ISSUER`), and confirms the bundled icon file exists under `public/`. Run this before editing the registry table by hand.
- **`node scripts/sodax-quote-check.mjs`** (same env var) quotes a fixed set of real pairs — including the two buy-direction stock cases, `100 USDC -> NVDA` and `700 USDC -> SPY` — through the same `@sodax/swaps-api` client the server routes use, proving package + base URL + request shape end to end. It deliberately has no sell-direction cases yet (`:103-107`).
- Beyond that, exercise the flow manually with a real mainnet wallet: a SODA pair (has a route both ways) and a stock/ETF/crypto pair bought with USDC or XLM (buy-direction only, per the current solver gap), including the destination-trustline-missing path, the insufficient-reserve path, a transient Horizon failure on the trustline check (retry-check affordance), and — hardest to trigger deliberately — a slow/ambiguous broadcast response (post-broadcast Close-not-Try-Again, explorer link with `srcTxHash`).
